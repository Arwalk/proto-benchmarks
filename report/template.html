Protobuf implementation benchmarks

Charts

Bars show the median over all timed rounds of all repeats. Tooltips show mean ± stddev, min/max and the number of rounds. Baseline is highlighted.

Tables

Cell: median ops/s (or selected metric), then the ratio against the baseline (>1 = faster than baseline). n/a = operation not supported by the library (hover for the reason). ⚠ = validation flag not fully satisfied (see Validation). ⏱ = the warm-up hit its cap before the throughput stabilised (3 consecutive 0.5 s probes within 5 %), so the runtime may still have been compiling or tiering during the timed rounds. A red value has a coefficient of variation above 5 % over its rounds: the machine was noisy or the runtime was not steady. Hover a cell for cv, round count and warm-up time.

Validation

Self-validation is reported by each harness; cross-validation parses every implementation's dumped output with the reference runtime (official Python protobuf / upb) and compares it with the fixture message, checks that the dumped wire output has the fixture's size, and walks the dumped JSON against the message descriptor to verify it is canonical ProtoJSON (lowerCamelCase keys, 64-bit integers as strings, enum names, base64 bytes, defaults omitted; whitespace is ignored).

Implementations and caveats

Methodology (short)

Each harness implements the same loop: calibrate a batch to ≥10 ms, warm up for , then run timed rounds of each and report raw (iterations, elapsed) pairs. All implementations decode the same fixture bytes and encode the same decoded message. Warm-up is a minimum of followed by 0.5 s probes until three consecutive probes agree within 5 % (cap ). One process at a time, pinned with taskset to the allowed CPU set (or to one core with --core); the whole suite is repeated in rotated order so thermal drift hits every implementation equally.
